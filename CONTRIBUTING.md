# Contributing to brandguard_flutter

Thanks for helping make white-label releases safer.

## Ground rules

- BrandGuard is **read-only**. No rule may modify, create or delete files in
  the validated project, run build tools, execute project code, or make
  network requests.
- Prefer false negatives over false positives. When a value cannot be
  resolved statically, report it as `info` with `Certainty.unresolved`
  instead of guessing. Heuristics must use `Certainty.heuristic` and default
  to `warning` or lower.
- Never print secrets. Pass any URL that might be printed through
  `redactUrl`.
- Keep output deterministic: sort anything derived from directory listings
  or maps.

## Development

```bash
dart pub get
dart format .
dart analyze          # must report no issues
dart test             # must pass
```

The test suite contains:

- `test/unit/` — configuration, parsers (Gradle, pbxproj, ARB/ICU, URLs) and
  every rule, using throw-away projects from `test/support/project_builder.dart`.
- `test/integration/` — the CLI (in-process and as a real process) and the
  static fixtures in `test/fixtures/`.

`test/fixtures/*` are generated by `dart run tool/generate_fixtures.dart`.
Edit the generator, not the fixture files. The broken fixture is
intentionally broken; its README lists every mistake, and the integration
test asserts the exact findings.

## Adding a rule

1. Implement `Rule` in `lib/src/rules/` with a stable snake_case `id`.
2. Report through `RuleReporter.fail` (configured severity), `report`
   (explicit, capped severity) and `pass`.
3. Register it in `BrandGuard.defaultRules()`.
4. Add tests covering a pass, a definite failure and the main false-positive
   case.
5. Document it in the README rule table and in `CHANGELOG.md`.

Rule IDs and the JSON schema are public API. Do not rename them in a minor
release.

## Pull requests

Describe the problem the change solves, include tests, and update the README
when behavior or configuration changes.
